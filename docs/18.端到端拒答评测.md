# 端到端拒答评测（30 题）：96.7%

- 日期：2026-11-17
- 目的：把「检索层误接受」和「最终回答有没有依据」分开度量——docs/17 之前只有单例证据
- 产物：`experiments/eval_e2e.jsonl`、`tools/evaluate_e2e.py`、`experiments/results/e2e_20261117/`

## 1. 方法

30 题，四类：

| 类型 | 题数 | 判定 |
| --- | --- | --- |
| answerable | 10 | 回答含预期关键值 = 答对；被拒 = 误拒；引用编号须指向真正含答案的片段 |
| no_answer_near | 10 | 应拒答（问同领域但不存在的属性：模具重量上限 / 整机噪声值） |
| no_answer_far | 5 | 应拒答（年假、班车、火星天气） |
| lure | 5 | 应拒答（保修期、厂家、噪声限值、产能、采购价格——都是"模型可能用常识补"的题） |

跑法：直接驱动 `ChatService.stream()`（真实检索 + 云端精排 + 本地 7B 生成），`temperature=0`，`use_rag=True`，每题独立会话。

判定：拒答 = `rag_status == no_hit` 或回答命中固定话术/「未收录」等措辞；答对 = 预期关键值出现在回答里（**按数字比**，抹平「乘 / ×」这类写法差异）；引用正确 = `【依据：知识片段N】` 指向的片段确实包含该关键值。

## 2. 结果

| 指标 | 数值 |
| --- | --- |
| 可回答：答对 | **10 / 10** |
| 可回答：误拒 | 0 |
| 带引用 / 引用正确 | 10 / **10** |
| 应拒答：拒答 | **19 / 20** |
| ├ 近域 | 9 / 10 |
| ├ 远域 | 5 / 5 |
| └ 常识诱导 | 5 / 5 |
| **整体通过率** | **96.7%** |
| 平均耗时 | 8.4 s（命中题约 20 s，拒答题 0.4–4.7 s） |

拒答题里 no_hit 的那部分几乎零成本——固定话术不调模型，0.4 s 返回；命中但被模型主动拒答的（L01 保修期）走了一次生成，约 15 s。

## 3. 唯一失败：数字挪用

E13「皮带输送线 CV-120 的模具重量上限是多少？」：

> 皮带输送线 CV-120 的模具重量上限是**每米 50 千克**【依据：知识片段1】。

文档里写的是「**额定载重** 50 千克每米」。检索没错（喂的就是 CV-120 手册）、引用编号也没错（片段 1 确实是那本手册），错在**模型把一个相邻语义的数字搬到了问题问的属性上**——而且带了引用，看起来完全可信。

这是 docs/17 §3 预判的"命中但片段不含答案"形态，也是目前唯一稳定复现的失败模式（两次运行都出现在同一题）。**严格提示词管得住"没有依据就拒答"，管不住"有依据但答的是另一个属性"。**

## 4. 评测本身踩的两个坑（值得记）

### 4.1 判定器把正确答案判成错的

E09「CMM-700 测量范围」的答案是 `700×1000×600 毫米`，预期值是 `700 乘 1000 乘 600 毫米`。第一版判定器用子串比 → 判成答错。改成**按数字比**（提取预期值里的数字，要求全部出现在回答中）后通过。写规则判定的人要注意：**中文里同一个数值有多种写法**。

### 4.2 云端精排整轮 SSL 失败

第二次跑时 30 次精排全部报：

```
SSLError(SSLEOFError(8, '[SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol'))
```

不是限流也不是 key 问题（重测单次 200 OK），是链路被对端偶发掐断。后果是**整轮静默回退 cosine**，评测跑出来的其实是 cosine 链路。

修法：`ApiReranker.score()` 加一次重试（网络类错误才重试，4xx 不重试）。重试后第三次跑没有出现回退。

顺带得到一个对照结论：**cosine 兜底那次，20 道应拒答题全部拒答**——说明拒答能力主要来自严格提示词，不依赖精排；精排影响的是答案质量（那次可回答题 9/10）。这也印证了"检索阈值治不了拒答、生成策略才治"的判断。

## 5. 三次运行对照

| 运行 | 链路 | 可回答 | 应拒答 | 通过率 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 第 1 次 | 云端精排正常 | 9/10 答对（1 例判定误判） | 19/20 | 93.3% | 判定器还没修 |
| 第 2 次 | **SSL 全挂 → cosine** | 9/10 答对 | **20/20 拒答** | 96.7% | 说明拒答不依赖精排 |
| 第 3 次 | 云端精排正常 + 判定器修好 | **10/10** | 19/20 | **96.7%** | 最终结果 |

## 6. 局限

1. **30 题、单模型**：只有本地 `deepseek-r1:7b`，换模型结论会变；题量也只够看方向，不足以下置信区间。
2. **判定是规则**：靠关键词判拒答、靠数字判答对，遇到"部分正确"或"换个说法"的答案会判错（E09 已经踩过一次）。
3. **lure 题偏构造**：5 道都是"文档里根本没有的属性"，真实场景的诱导往往更隐蔽（如问一个存在但过期的数值）。
4. **没有人工复核**：30 条答案建议人工再过一遍，尤其 E13 这类"有引用但答错属性"的。

## 7. 下一步（按性价比）

1. **数字级 grounding 校验**：生成后解析回答里的数字，要求每个数字都能在引用片段原文中找到；找不到就把答案降级成「该数字未在知识库中找到依据」。这能直接堵住 E13 这类失败，工作量约半天。
2. 把 30 题扩到 60–80 题，补"过期数值""部分匹配"两类。
3. 换更高一档的生成模型再跑一遍，区分"检索/策略问题"与"模型能力问题"。
