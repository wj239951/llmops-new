## 2. 多轮检索改写（新增）

### 2.1 问题

`chat_service._apply_rag()` 用 `clean_query` 检索，而 history 只传给生成模型。于是第二轮的"那它的更换周期呢"会丢掉主体，向量与 BM25 同时跑偏——闸门按无答案处理。

### 2.2 实现

新增 `app/services/query_rewrite.py`：

- **只改检索查询**：原文继续用于展示、写库与生成（`final_query` 不变）；
- **三种模式**：`off`（默认）/ `rule`（零延迟，从头几轮抽型号回填指代）/ `llm`（模型改写，带少样本与 JSON 输出）；
- **触发条件**：有 history，且查询不带型号（多轮里不带型号的问句几乎一定是省略）；带型号且无指代时不动（已是自包含查询）；
- **三重回退**：llm 失败或超时 → rule；rule 失败 → 原句；改写后没召回到东西 → 用原句再检一次；
- **型号保真**：改写结果必须保留原句里的型号/编号，丢了自动补回（exact bypass 依赖它）。

接入点在 `chat_service._apply_rag()`：

```python
search_query, rewrite_meta = query_rewrite.rewrite(query, ctx.get("history") or [])
rag_docs = self.rag.search(db, search_query, use_rerank=req.use_rerank, ...)
if not rag_docs and search_query != query:          # 改坏了就退回原句
    rag_docs = self.rag.search(db, query, ...)
```

`meta` / `done` 事件新增 `rewrite` 字段（mode / via / changed / query / fallback / ms），前端可显示"本轮检索用的是哪句话"。

### 2.3 效果

`tools/evaluate_rewrite.py` 跑 `experiments/eval_multiturn.jsonl` 的 20 段会话，只评第 2 轮（第 1 轮用来建历史）：

| 模式 | 第 2 轮 hit@3 | top1 | 触发改写 |
| --- | --- | --- | --- |
| off（线上旧行为） | **15.0%** | 10.0% | 0 |
| rule（新默认） | **100.0%** | 55.0% | 20/20 |

20 段全部触发，hit@3 从 15% 提到 100%。

第一版触发器带了个"长度 ≤12 字"的条件，只触发 18 段、hit@3 停在 90%——漏掉的正是 `合模机构间隙检测多久一次？` 这种**超过 12 字但同样没主语**的省略句。把长度阈值整个去掉、改成"多轮且不带型号就补主体"之后，触发到 20/20、hit@3 100%。**长度不是可靠信号，缺主语才是。**

**top1 只有 55% 是规则改写的天花板**：它只是把主体拼回去，措辞仍是口语（`zx-1200 的最大注射量呢？`），排序不如正式问句。要再往上得用 llm 模式，代价是每轮一次模型调用（见 2.4）。

### 2.4 llm 模式实测（小样本）

用本地 `deepseek-r1:7b`，把改写超时从默认 1.5s 放宽到 120s，跑前 6 段：

| 项 | 结果 |
| --- | --- |
| 单次改写耗时 | **19.6–28.7 s**（4 段成功改写） |
| 改写质量 | 明显好于 rule：`注塑机 ZX-1200 的锁模力是多少`、`螺杆空压机 GA-55 的额定排气量是多少`——补全主语、去掉口语 |
| hit@3 / top1 | 与 rule **持平**（6 段上都是 67% / 67%） |

两个结论：

1. **默认 1.5s 超时 + 本地推理模型 = 静默退化成 rule**。上一轮整批 llm 模式跑了 13 分钟，实际全部超时回退，改写结果与 rule 逐字相同——回退机制工作正常，但"开了 llm 模式"并不等于"用上了模型"。
2. **瓶颈在触发、不在措辞**：6 段样本里 rule 失败的 2 段，失败原因是"压根没触发改写"，而不是"改写得不好"。修掉触发条件后 rule 已经 20/20。所以 llm 模式的价值要等真实对话（省略更模糊）才好评估，现阶段不值得为它付出 20s 延迟。

### 2.5 成本与影响面

- rule 模式：`<1 ms`，纯字符串操作，不引入依赖；
- 单轮请求（无 history）完全不触发，线上老路径零变化；
- 改写失败不阻断问答（最差退回原句，等价于旧行为）。

## 3. 阈值路由：试算后不落地

docs/13 §4.1 显示 exact 类最优 0.71、paraphrase 类最优 0.59，看起来该按题型分档。用同一批 183 题试算（分类器：含"是多少/怎么/哪些"判 formal，含"咱们/大概/呢"判 colloquial）：

| 策略 | 正确覆盖 | 无答案误接受 |
| --- | --- | --- |
| 全局 0.56（新默认） | 100.0% | 71.4% |
| 全局 0.60 | 98.0% | 57.1% |
| 路由（formal 0.68 / colloquial 0.56） | 98.6% | 48.6% |

路由确实比全局 0.60 更好一点（+0.7pp 覆盖、−8.6pp 误接受），但**不落地**，原因有两个：

1. 相对 0.56 仍要丢 1.4pp 覆盖，收益不足以抵消引入的复杂度；
2. 分类器是照着本批题库的问法拟的启发式，本质上在拟合题库风格——换真实提问大概率失效，属于典型的过拟合。

**结论**：保持单一阈值，把拒答交给精排（0.90）与模型侧策略；等积累真实提问日志后再评估分档。

## 6. 局限

1. **llm 模式在线上不可用**：本地 `deepseek-r1:7b` 单次改写 20–29 s，远超默认 1.5s 超时，会静默退回 rule（实测整批跑完与 rule 逐字相同）。要用 llm 模式，得换小模型（1–2B）或云端 API，并重新标定超时。
2. **多轮题库是合成的**：20 段都带明确型号，且第 2 轮的问法是为"指代/省略"设计的；真实对话里的省略更模糊（"那个呢""换成圆的那款呢"），rule 模式靠型号回填可能失效。
3. **改写只解决检索侧**：上一轮答案错了、下一轮基于错误实体继续问，改写会忠实地把错误实体带下去。
4. **rule 模式的边界**：12 字以内的自包含短问句（"液压油有哪些品牌？"）也会被拼上主体，可能引入轻微偏移——这是规则改写的固有代价，llm 模式靠提示词可以避免。
