# 输入清洗的端到端检索评测

> [docs/08](08.输入清洗接入报告.md) 只量化了「清洗还原率」和「耗时」，没回答一个问题：
> **清洗到底能不能让检索变好？** —— 那 45 条评测题本身是干净手写问句，清洗对它们是 no-op。
> 本报告补上这块证据：把评测题弄脏，看清洗前后的检索指标。

## 1. 方法

不启动服务、不连 MySQL，直接复刻检索层（`tools/evaluate_clean_retrieval.py`）：

```
mysql-init/llmops_db.sql  ──解析──► 11 篇文档
                                    │
                    RecursiveCharacterTextSplitter(500/50, 中文标点分隔)
                                    ▼
                                 21 个片段 ──bge-m3(Ollama)──► 向量库
                                    ▲
   75 条评测题 ──┬─ clean   ：原句
   （45 自然语言 + 15 编号 + 15 短查询）
                 ├─ dirty   ：注入噪声后原样检索
                 ├─ rule    ：脏句 → 规则清洗 → 检索
                 └─ model   ：脏句 → 0.8B 蒸馏模型清洗 → 检索
                                    │
                                    ▼
                    cosine top-6 → 与 expected_doc_ids 比对
```

指标沿用 `tools/evaluate_rag.py` 的定义：recall@K、hit@3、MRR、top1（同篇多 chunk 只算首次出现）。

**噪声分两档**，都按固定随机种子生成：

| 档位 | 注入内容 | 对应真实场景 |
|---|---|---|
| `mild` | 零宽字符、全角字母数字、标点后多余空格、手抖重复字 | 在聊天框里手打 / 输入法 |
| `heavy` | mild + `&nbsp;` 实体、`<p>` 包裹、句中硬折行 | 从网页 / PDF 复制粘贴 |

> 折行**只切在汉字之间**。第一版按字符串中点盲切，把 `E-073` 劈成 `E-0` + `73`、
> 把 `&nbsp;` 劈成 `&nbs` + `p;`——那是夹具自己制造的假故障（真实排版不会在 token 内部折行），
> 修正后重测，见 §4。

## 2. 结果：总体

75 条题（含 8 条无答案题，按定义 recall 为 0，不参与下面这轮对比）：

| 条件 | recall@6 | hit@3 | MRR | top1 |
|---|---|---|---|---|
| clean（干净原句） | 86.7% | 86.7% | 0.831 | 80.0% |
| dirty（mild，不清洗） | 86.7% | 85.3% | 0.819 | 78.7% |
| **rule**（mild） | **86.7%** | **86.7%** | **0.831** | **80.0%** |
| **model**（mild） | **86.7%** | **86.7%** | **0.831** | **80.0%** |
| dirty（heavy，不清洗） | 85.3% | 84.0% | 0.814 | 78.7% |
| **rule**（heavy） | **86.7%** | **86.7%** | **0.831** | **80.0%** |
| **model**（heavy） | **86.7%** | 85.3% | 0.828 | 80.0% |

总体的伤害很小（mild 只掉 1.4pp hit@3），原因是 bge-m3 对长句里的噪声相当鲁棒，
而 75 条里有 60 条是长句。**伤害集中在短查询**——见下。

## 3. 结果：伤害集中在「搜索框短查询」

按题型拆开（`token_query` = 15 条类似搜索框的短查询，如 `E-073`、`SX 编号`、`125g`）：

| 条件 | MRR | hit@3 | top1 |
|---|---|---|---|
| clean | 0.689 | 86.7% | 53.3% |
| dirty（mild） | 0.628 | 80.0% | 46.7% |
| **rule / model（mild）** | **0.689** | **86.7%** | **53.3%** |
| dirty（heavy） | 0.606 | 73.3% | 46.7% |
| **rule（heavy）** | **0.689** | **86.7%** | **53.3%** |
| model（heavy） | 0.672 | 85.3% | 53.3% |

其余三类（`exact` 21 条、`paraphrase` 16 条、`exact_token` 15 条）在四种条件下
**全部 100%**，噪声完全没影响——这也解释了为什么总体指标看起来"没变化"。

短查询为什么最脆：它没有上下文可依托，`E-073` 里混进一个零宽字符或全角数字，
整条查询的语义就散了；而长句里同样的噪声只占很小权重。这与 [docs/06](06.混合检索实验报告.md)
的结论一致——短查询本来就是 dense 检索的薄弱环节，也是混合检索收益最明显的地方。

## 4. 评测反过来修掉了清洗器的三个缺陷

这轮评测最有价值的产出不是指标，是**它暴露了清洗器本身的 bug**（都已修复）：

1. **短查询的折行永远合并不了**：合并条件写的是「上一行 ≥24 字」，那是给长文档设计的，
   而搜索框查询整句往往不到 24 字，从 PDF 复制时被折成两行就再也接不回去。
   → 短文本（≤120 字）放宽这条阈值。
2. **跨行的重复字压不掉**：先把 `多少少\n少少` 按行压重复（3 次→1 次、2 次保留），
   再合并，结果是 `多少少少`。→ 调整顺序为「先合并、后压重复」。
3. **型号被拆开时补了空格**：`Ｅ-\n073` 合并成 `E- 073`，正确是 `E-073`。
   → 只有两侧都是字母/数字时才补空格。

修完之后：规则通道的**精确还原率 97%**（mild 与 heavy 相同），且 heavy 下的检索指标
与干净基线逐位相同。

## 5. 结论与取舍

- **清洗确实有价值，但只在短查询上可测**：heavy 噪声下短查询 hit@3 73.3% → 86.7%、
  MRR 0.606 → 0.689，回到干净基线。长句本来就扛得住，清洗带来的提升在噪声范围内。
- **默认仍然用 `rule`**：mild/heavy 两档都能完全还原，耗时 0.06–0.74ms；
  模型通道在 heavy 上还原率只有 55%（把 `E-073` 读成 `E-073 `、多删一个空格等），
  指标略低于规则（MRR 0.828 vs 0.831），且单次 0.4s——它是"长段落/PDF 整篇粘贴"的增强项，
  不是短查询的必需品。
- **收益上限受检索器本身限制**：短查询 clean 的 hit@3 也只有 86.7%，
  说明还有别的原因（编号类查询语义稀薄），清洗只是把噪声造成的额外损失补回来。

## 6. 局限

- 语料只有 11 篇 / 21 个片段，属于小样本；换语料需重跑。
- 无答案题（8 条）不适用于 recall，本报告没评"清洗是否影响拒答"（那需要阈值侧实验）。
- `heavy` 档的 `&nbsp;` 与 `<p>` 是模拟值，真实网页结构更复杂（嵌套标签、表格）。
- 模型通道的还原率随噪声强度下降明显（83% → 55%），说明它在字符级改写上不如规则稳定；
  这与 [docs/08](08.输入清洗接入报告.md) §3.3 的还原率实验互相印证。

## 7. 复现

```bash
cd llmops-backend
.venv/Scripts/python.exe tools/evaluate_clean_retrieval.py --suite all --noise mild
.venv/Scripts/python.exe tools/evaluate_clean_retrieval.py --suite all --noise heavy

# 产物
experiments/results/clean_retrieval_all_mild.{csv,json}
experiments/results/clean_retrieval_all_heavy.{csv,json}
```

前置条件：Ollama 跑着且已 `ollama pull bge-m3`；
要跑 `model` 条件还需 `python tools/clean_server.py --model <权重目录>`。
