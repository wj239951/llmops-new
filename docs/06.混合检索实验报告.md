# 混合检索实验报告（BM25 + bge-m3 + RRF）

> 对应代码：`llmops-backend/app/services/hybrid_service.py`、`rag_service.py` 的 `_dense_chunks / _rrf_fuse / _hybrid_candidates`
> 对应开关：`RAG_HYBRID_ENABLED`（默认 `false`，无额外依赖）
> 评测脚本：`llmops-backend/tools/evaluate_hybrid.py`
> 结果文件：`experiments/results/hybrid_compare.csv`、`hybrid_per_query.csv`、`hybrid_summary.json`

## 1. 背景：为什么把注释掉的 jieba 接回来

项目第一代用的是「jieba 分词 + MySQL `LIKE`」关键词检索，后来因为整句中文提问命中率太低，换成了 bge-m3 向量检索，旧实现整段注释留在 `rag_service.py` 里。

向量检索的强项是语义（改写、同义、口语化），弱项是**精确 token**：型号、编号、指标值这类字符在 embedding 里几乎不占权重。知识库里恰好大量存在这类内容（`RL-2077`、`E-073`、`KYN28`、`0.15MPa`、`19.5%–21%`、`WNS2-1.25-Q`）。当用户在搜索框里只输入一个编号时，向量召回可能把正确片段排在候选池之外——这是纯 dense 检索的结构性短板，和阈值无关。

因此把旧 jieba 关键词通道重新接回来，做成**可选的混合检索**：dense（bge-m3）+ sparse（jieba/BM25）双路召回，RRF 融合，再交给可选的 rerank 精排。默认关闭，不改变现有链路。

## 2. 方案设计

```
query
 ├─ dense:  bge-m3 → Chroma 取 top RAG_HYBRID_DENSE_K=12   ┐
 └─ sparse: jieba 分词 → 内存 BM25 取 top SPARSE_K=12      ┘
                    ↓ RRF 融合（k=60）
              候选按 RRF 分数排序，取前 candidate_k（线上 = RAG_RERANK_CANDIDATE_K 或 RAG_CANDIDATE_K）
                    ↓
        ┌─ 开启 rerank：bge-reranker-v2-m3 精排 → 精排阈值 → top RAG_FEED_TOPK
        └─ 未开 rerank：按 cosine 分数重排 → cosine 阈值 → top RAG_FEED_TOPK
```

关键设计取舍：

- **RRF 而不是加权分数相加**：BM25 与 cosine 分数尺度不同，RRF 只用名次（`1/(k+rank)`），不需要标定权重，换语料也不用重调。
- **BM25 索引从 Chroma 懒加载**：不新增存储/文件；首次检索时从 `vectorstore._collection.get(include=["documents","metadatas","embeddings"])` 建内存索引（当前 21 条向量，毫秒级）。文档增删改后 `invalidate()` 失效重建，不会读到旧数据。
- **BM25 独有候选要补齐 cosine 分数**：融合后的候选如果只有 BM25 命中，其 `RetrievedChunk.score` 用存储向量与 query 的 cosine 补算，保证下游「按 cosine 排序/过滤」的语义不变；反查 MySQL 失败（孤儿向量）则记 warning 跳过。
- **三级回退**：hybrid 索引不可用 → 自动退回 dense；rerank 不可用 → 自动退回 cosine。任何一层出问题服务都不崩，只降级并打日志。
- **分词保留型号/编号**：先按 `[a-z0-9]+(?:[-_.][a-z0-9]+)*` 整体抽出英文/数字/型号 token（`rl-2077`、`e-073`、`0.15mpa`），再对剩余中文用 `jieba.lcut_for_search`（长度 ≥2），最后过滤 `Disable_word_list.txt` 停用词——复用旧代码的停用词表。

## 5. 结果

### 5.1 总表（`experiments/results/hybrid_compare.csv`）

| 题库 | 模式 | recall@6 | MRR | coverage | hit@3 | top1 | 误接受 | 平均耗时 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| eval_qa（45 题） | dense | 100.0% | 1.0000 | 100.0% | 100.0% | 100.0% | 100.0% | 49.8ms |
| eval_qa | hybrid | 100.0% | 1.0000 | 100.0% | 100.0% | 100.0% | 100.0% | 58.4ms |
| eval_qa | dense+rerank | 100.0% | 1.0000 | 97.3% | 97.3% | 97.3% | 0.0% | 4180.3ms |
| eval_qa | hybrid+rerank | 100.0% | 1.0000 | 97.3% | 97.3% | 97.3% | 0.0% | 4353.7ms |
| hard（15 题） | dense | 100.0% | 0.9667 | 93.3% | 93.3% | 86.7% | 0.0% | 44.7ms |
| hard | hybrid | 100.0% | 0.9667 | 93.3% | 93.3% | 86.7% | 0.0% | 52.7ms |
| hard | dense+rerank | 100.0% | 1.0000 | 73.3% | 73.3% | 73.3% | 0.0% | 4336.4ms |
| hard | hybrid+rerank | 100.0% | 1.0000 | 73.3% | 73.3% | 73.3% | 0.0% | 4330.5ms |
| token（15 题） | dense | 86.7% | 0.5889 | 13.3% | 6.7% | 6.7% | 0.0% | 41.1ms |
| token | hybrid | **100.0%** | 0.6167 | 13.3% | 6.7% | 6.7% | 0.0% | 53.2ms |
| token | dense+rerank | 86.7% | 0.8222 | 26.7% | 26.7% | 26.7% | 0.0% | 4175.1ms |
| token | hybrid+rerank | **100.0%** | **1.0000** | **46.7%** | **46.7%** | **46.7%** | 0.0% | 4065.0ms |

### 5.2 结论一：自然语言题库上，混合检索与 dense 完全相同

eval_qa 与 hard 两个题库上，dense 的 recall@6 本来就是 **100%**——正确片段已经在 dense 候选池里，BM25 只是把同一批片段以不同名次再排一遍，最后按 cosine 重排后结果不变（hard 库的 MRR/hit 差异为 0）。**在这两套题库上，混合检索没有可测量的收益**，额外成本是 8–9ms/次（BM25 打分 + RRF 融合；索引只建一次）。

这也回答了「为什么之前 README 只说 dense+rerank」：在这份语料上，dense 召回已经饱和，混合检索的收益被掩盖了。

### 5.3 结论二：搜索框式短查询上，混合检索补上了 dense 漏召回

token 题库模拟「只输一个编号/指标」的搜索场景，收益是真金白银的：

- recall@6：**86.7% → 100%**（dense 漏掉的 2 条被 BM25 捞回：`19.5%–21%`、`25m 水带`）；
- 开精排后：hit@3 **26.7% → 46.7%**（4/15 → 7/15），MRR **0.8222 → 1.0000**，top1 准确率 **26.7% → 46.7%**，coverage 同样提升；耗时基本不变（精排耗时占绝对大头）。
- 具体收益题：`t01 RL-2077`、`t02 E-073`、`t07 19.5%–21%`——dense 候选池里要么没有正确片段，要么同分片段把 rerank 分数拉低；BM25 精确命中把正确片段顶上来后，精排分越过 0.76 阈值，才真正喂给模型。

### 5.4 结论三：rerank 仍是「拒答」的主力，混合检索不改变这一点

- 45 条主库上，纯 cosine（dense/hybrid）对 8 条无答案问题误接受率 **100%**；开 rerank 后降到 **0%**。混合检索对无答案问题没有额外帮助（BM25 的精确 token 反而容易把近域问题命中，好在精排分数压得住）。
- hard 库上，混合检索没有改善 rerank 的覆盖率（73.3%）：4 条精确编号长问句（h04 `0.15MPa`、h07 `O₂ 19.5–21%`、h12 `125g/48h`、h13 `CW 编号`）虽然都被精排排到第 1，但精排分低于 0.76 被阈值过滤——**阈值是按自然语言题库标定的，对编号类问题偏严**，这是后续要单独标定的点。
- 短查询同样暴露这个问题：token 库开精排后 coverage 只有 46.7%（7/15），剩下 8 条是「排名第 1 但精排分 <0.76」被拒。混合检索提高了召回上限，但绝对阈值仍然卡脖子。

## 6. 代价

| 项 | 数值 |
| --- | --- |
| 额外依赖 | 无（jieba 已是常规依赖；BM25 纯 Python 实现，不引 rank_bm25） |
| 索引内存 | 21 条向量 × 1024 维 + 分词结果，当前可忽略；语料规模到万级需评估 |
| 额外延迟 | 纯召回模式 +8.5~12ms/次（首次请求含一次索引构建） |
| 开启方式 | `llmops-backend/.env` 设 `RAG_HYBRID_ENABLED=true` 后重启后端；默认关闭 |
| 失败回退 | 索引构建失败 / 停用词表缺失 / Chroma 不可用 → 自动退回纯 dense，打 warning，不影响服务 |

## 7. 复现

```bash
cd llmops-backend
# 四模式 × 三题库（约 14 分钟，CPU 精排占绝大部分）
.venv\Scripts\python.exe tools/evaluate_hybrid.py
# 只跑召回层两种模式（秒级）
.venv\Scripts\python.exe tools/evaluate_hybrid.py --skip-rerank
```

输出：`experiments/results/hybrid_compare.csv`、`hybrid_per_query.csv`、`hybrid_summary.json`。

单元测试：`pytest -q`（27 passed，其中 hybrid 6 条、rerank 4 条，默认关闭不加载模型）。

## 8. 局限与下一步

- **收益只出现在 dense 漏召回的语料/查询形态上**。当前 11 篇语料对 bge-m3 太简单，自然语言题库 dense 召回 100%；真正能体现混合检索价值的是更大语料（长文档、专业缩写、稀有型号）或搜索框式短查询。本报告用 token 题库把这一收益显式测出来了，但不能夸大成「所有场景都提升」。
- **BM25 索引是进程内内存索引**：22 条向量没有压力，文档量上千后应考虑持久化倒排（如 SQLite FTS5/Elasticsearch）或限制 `hybrid_dense_k`。
- **精排阈值对短查询/编号类问题偏严**（0.76 标定自自然语言题库）。下一步应按题型分别标定，或改用「top1-top2 相对间隔」替代绝对阈值。
- **RRF 参数未扫**（`rrf_k=60` 是常用默认）；候选池 12+12 也未调优，语料变大后需要重扫。
- 短查询下 BM25 的 `k1/b` 未按中文短文本调参，仍是通用默认值。

## 9. 环境

- 时间：2026-11-04
