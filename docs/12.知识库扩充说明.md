# 知识库扩充：11 篇 → 44 篇（附扩充前后检索对照）

- 日期：2026-11-17
- 范围：`mysql-init/02_knowledge_expand.sql`（新增种子）、`mysql-init/Dockerfile`（挂进 initdb）、`experiments/results/expand_20261117/`（对照评测产物）
- 不改代码：本次只加数据，检索链路、阈值、开关全部沿用现状

## 1. 为什么扩

原语料 11 篇 / 21 条向量，所有检索指标已经饱和：

| 现象 | 出处 |
| --- | --- |
| dense 在 45 题主库上 recall@6 = 100%，MRR = 1.0000 | docs/06 §5.1 |
| 因此「混合检索没有可测量的收益」，RRF 与精排的价值被语料规模掩盖 | docs/06 §5.2 |
| 满分为 100% 的指标无法区分配置好坏，阈值标定也失去意义 | docs/04 §8 局限 2 |

一句话：**在 21 条向量上，任何配置都是满分；要验证链路，先让语料不再饱和。**

## 3. 怎么落

1. **种子**：`mysql-init/02_knowledge_expand.sql`，33 条 `INSERT ... ON DUPLICATE KEY UPDATE`，重复执行不会重复插入；已对现有库验证只跑幂等（两次执行后仍是 44 篇 / 26,002 字）。
2. **新装环境**：`mysql-init/Dockerfile` 增加一行 `COPY`，initdb 按文件名顺序执行（01 建表 → 02 灌数据），不需要额外步骤。
3. **存量环境**：导入 SQL 后必须重建向量，否则新文档检索不到：
   ```bash
   mysql -h 127.0.0.1 -u root -p --default-character-set=utf8mb4 < mysql-init/02_knowledge_expand.sql
   cd llmops-backend && .venv\Scripts\python.exe tools/reindex_knowledge.py
   ```
   本次执行结果：`待重新向量化：44 篇文档 … 完成，共写入 86 条向量`。

## 4. 扩充前后对照

同一脚本（`tools/evaluate_hybrid.py --skip-rerank`）、同一题库，**只换语料**。左列取 docs/06 的基线，右列为本次结果（产物在 `experiments/results/expand_20261117/`）。

| 题库 | 模式 | recall@6 | MRR | hit@3 | top1 | 误接受 |
| --- | --- | --- | --- | --- | --- | --- |
| eval_qa（45 题） | dense 21→86 | 100.0% → 100.0% | **1.0000 → 0.8176** | 100% → 97.3% | **100% → 67.6%** | 100% → 100% |
| eval_qa | hybrid 21→86 | 100.0% → 100.0% | **1.0000 → 0.8311** | 100% → 97.3% | **100% → 70.3%** | 100% → 100% |
| hard（15 题） | dense | 100% → **93.3%** | 0.9667 → 0.8167 | 93.3% → 80.0% | 86.7% → 66.7% | 0% → 0% |
| hard | hybrid | 100% → **100%** | 0.9667 → 0.8300 | 93.3% → 80.0% | 86.7% → 66.7% | 0% → 0% |
| token（15 题） | dense | 86.7% → **53.3%** | 0.5889 → 0.3000 | 6.7% → 6.7% | 6.7% → 6.7% | 0% → 0% |
| token | hybrid | 100% → **93.3%** | 0.6167 → 0.3833 | 6.7% → 6.7% | 6.7% → 6.7% | 0% → 0% |

### 结论一：之前的满分是语料规模的假象

换语料后 dense 的 top1 直接从 100% 掉到 67.6%，MRR 从 1.0000 掉到 0.8176。代码一行没改，说明 **21 条向量上的「满分」不代表链路好，只代表候选比答案还少**。

### 结论二：混合检索第一次显出可测量的价值

- hard 题库：dense 93.3% → **hybrid 100%**（补回 1 条精确编号漏召回）
- token 题库：dense **53.3%** → **hybrid 93.3%**（补回 6 条）
- eval_qa：MRR 0.8176 → 0.8311，top1 67.6% → 70.3%

这与 docs/06 §5.2「两套题库上混合检索没有可测量收益」的结论**并不矛盾**：当时 dense 已饱和，没有可补的空间；现在有了。可以说，`RAG_HYBRID_ENABLED` 的价值从这次扩充之后才真正可验证。

### 结论三：短查询（token 库）仍是重灾区

recall 靠 BM25 救回来了，但 **hit@3 只有 6.7%**——正确片段进了候选池，却过不了 0.53 的 cosine 闸门（coverage 低）。这是 docs/11 已经指出的「阈值对编号类偏严」，扩充语料后依然存在，且更明显。

### 结论四：误接受率与语料规模无关

dense/hybrid 在 eval_qa 上仍是 100% 误接受，与扩充前一致——这是单阈值的原理性上限（docs/04 §7：正确题与无答案题的 top1 分数区间重叠），只有精排或模型侧拒答能解。

### 结论五：重复片段开始吃满 top-3

扩充后每篇文档多为 2 个片段，实测出现同一文档占满 2 条（如 `GA-75`、`动火`、`成品仓库` 三例），这与 docs/11 讨论的「full(片段) vs full(文档)」是同一个问题。语料小时影响有限，文档一多就是稳定损耗。

## 5. 局限与下一步

1. **题库没有跟着扩**：`eval_qa*.jsonl` 的 `expected_doc_ids` 仍只覆盖原有 11 篇，新文档目前只当干扰项。要评测新文档，得补题（建议每篇 1–2 条，重点覆盖五组兄弟文档的「主体区分」）。
2. **阈值必须重扫**：0.53 / 0.76 都是在 21 条向量下标定的，现在候选分布已变（正确片段分数从 0.58–0.76 掉到 0.50–0.74 一档），建议按 docs/04 的方法重跑 `tools/evaluate_rag.py` 与 docs/05 的精排扫描。
3. **doc 级去重缺失**：`search()` 的 `passed[:feed_topk]` 仍在片段序列上截断，同一文档可占多个名额；建议按 `(doc_id)` 去重后再取 top-3（约 5 行改动），但属于代码变更，本次未动。
4. **规模仍偏小**：44 篇 / 86 片段比 21 条好得多，但离「十万级片段」的工程边界还远，混合索引（内存态）与阈值稳定性仍需更大语料验证。
