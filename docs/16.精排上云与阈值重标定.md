# 精排上云（SiliconFlow）与阈值重标定

- 日期：2026-11-17
- 前置：docs/15（本机 6 GB 显存跑不动「7B 聊天 + 2.27 GB 精排权重」，GPU 精排 CUDA OOM，静默回退 cosine）
- 结论：精排切到硅基流动 `/rerank` API，阈值由 0.90 调到 **0.92**

## 1. 为什么上云

| 方案 | 单问精排耗时 | 显存 | 结论 |
| --- | --- | --- | --- |
| local + GPU（原配置） | 258 ms | 2.27 GB | **6 GB 机器 CUDA OOM**，与 7B 模型抢显存，静默退回 cosine |
| local + CPU | 4649 ms | 0 | 能用，但整体 23 s/问 |
| **cloud（本次）** | **405 ms（中位 387，最大 1301）** | 0 | 采用 |

云端不占显存，延迟比本地 GPU 多约 150 ms、比本地 CPU 快一个数量级。

## 2. 配置

`.env`：

```ini
RAG_RERANK_ENABLED=true
RAG_RERANK_PROVIDER=cloud
RAG_RERANK_API_BASE_URL=https://api.siliconflow.cn/v1
RAG_RERANK_API_MODEL=BAAI/bge-reranker-v2-m3
RAG_RERANK_API_TIMEOUT=10
RAG_RERANK_SCORE_THRESHOLD=0.92
```

key 走**系统环境变量** `SILICONFLOW_API_KEY`（`RAG_RERANK_API_KEY` 留空即复用它），不写进 `.env`、不进仓库。

实现走 `ApiReranker`（`app/services/rerank_service.py:137`）：

- `load()` 只校验配置、不发网络请求，启动零开销；
- `score()` 一次批量请求 6 个片段，失败抛 `RerankerUnavailableError` → 调用方回退 cosine，服务不崩；
- 响应里按 `index` 回填 `relevance_score`，与本地 sigmoid 分数语义一致。

**踩到的坑**：环境变量是 `setx` 写到 **Machine 作用域**的，而已经跑着的终端（包括本次的 DSH shell）进程环境里没有它，`settings.SILICONFLOW_API_KEY` 读到空串 → 精排直接判为不可用并回退 cosine。新开一个终端启动后端就没问题；在既有 shell 里要显式注入：

```powershell
$env:SILICONFLOW_API_KEY = [Environment]::GetEnvironmentVariable('SILICONFLOW_API_KEY','Machine')
```

## 3. 阈值重标定（183 题）

模型与本地完全相同（`BAAI/bge-reranker-v2-m3`），分数尺度可直接沿用，但仍按 docs/05 的方法重扫了一遍（`experiments/results/rerank_cloud_20261117/`）：

| 精排阈值 | 覆盖 | top1 | 误接受（near） | balanced acc |
| --- | --- | --- | --- | --- |
| 0.88 | 97.3% | 90.5% | 15.0% | 94.4% |
| 0.90 | 96.6% | 89.9% | 10.0% | 95.5% |
| **0.92（采用）** | **96.6%** | **89.9%** | **5.0%** | **96.9%** |
| 0.94 | 96.0% | 89.2% | 5.0% | 96.5% |
| 0.95 | 95.3% | 88.5% | 0% | 97.6% |

**0.92 严格优于 0.90**：覆盖与 top1 完全相同，只因一条近域误接受（0.9099）被挡住，误接受从 5.7% 降到 2.9%。免费。

**为什么不取脚本推荐的 0.95**：

1. 覆盖要掉 1.35pp（丢 2 道正确题）；
2. 更要命的是 `weak_hit` 判据是 `top1 >= 阈值 + 0.06`，0.95 + 0.06 = **1.01**，任何非 exact 命中都会被判成弱命中，前端会全程降级显示。

## 4. 端到端验证（同一套冒烟）

| 用例 | rag_status | 喂进去的片段 | 结果 |
| --- | --- | --- | --- |
| 单轮：ZX-1200 锁模力 | hit | 1 条（0.998） | 「1200 千牛」✅ |
| 近域无答案：ZX-1200 模具重量上限 | **no_hit**（原为 hit） | **0 条** | 见 §5 ⚠️ |
| 多轮第 1 轮：最大注射量 | hit | 1 条（0.996） | 「260 克」✅ |
| 多轮第 2 轮：那它的滤芯多久换一次 | hit | 3 条（0.959 / 0.957 / 0.939） | 「每 400 小时」✅ |

`score_mode=rerank`、`rerank_available=True` 全程成立。**近域无答案题第一次被真正拦住**（cosine 时代是 `hit` + 3 条引用），说明 0.92 起作用了。

## 5. 但是：拦住了检索，没拦住模型

`rag_status=no_hit` 的那道题，模型回答是：

> ZX-1200 型号的注塑机模具重量上限通常为 1,000 公斤。建议在实际操作中进行测试以确保安全性。

上下文是空的，模型凭预训练知识**编了一个具体数字**。这正是 docs/15 §3 指出的"检索与生成策略不一致"：闸门在收紧、prompt 在放松（`如果知识库内容不足，请说明不足，再结合通用知识补充`）。

现在证据链完整了：

- 检索层：0.92 把误接受从 74%（cosine）压到 2.9%；
- 生成层：一句"结合通用知识补充"把收益还回去——用户看到的是条没有引用、但语气确定的错误数字。

**这是下一个必须做的事**（P1 拒答策略对齐）。

## 6. 成本与延迟

| 项 | 数值 |
| --- | --- |
| 单次精排 | 405 ms 均值 / 387 ms 中位 / 1301 ms 最大（网络抖动） |
| 单次 token | 6 片段约 150 input tokens |
| 183 题标定 | 约 2.7 万 tokens，1.5 分钟 |
| 失败行为 | 超时/限流/断网 → `RerankerUnavailableError` → 回退 cosine，`meta.rerank_available=false` |

## 7. 回滚

```ini
RAG_RERANK_PROVIDER=local
RAG_RERANK_DEVICE=cpu        # 本机 GPU 与 7B 模型抢显存，只能 CPU
RAG_RERANK_SCORE_THRESHOLD=0.90   # 本地 sigmoid 刻度
```

## 8. 局限

1. **强依赖外网**：断网时静默回退 cosine（阈值会自动切回 0.56 那一档吗？不会——`active_score_config` 用的是 `rag_status` 判定的 score_mode，回退后阈值会跟着切回 `RAG_SCORE_THRESHOLD`，这点代码是对的）。
2. **分数尺度绑定服务商**：换模型（如 Jina / Cohere）必须重扫阈值，docs/05 的方法可直接复用。
3. **多轮短查询的兄弟文档仍会漏过**：第 2 轮里 `11_ZX-2030巡检手册` 以 0.939 混进了 top-3（正确答案 0.957 排第二），说明口语化改写后精排对"型号差一位"的区分力下降——与 docs/14 §2 的 top1 只有 55% 是同一件事。
