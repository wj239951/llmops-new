# 闸门口径统一 + 分解层进入默认链路

> 此前所有检索数字都是**无阈值**口径（"top-K 里有没有"），线上却是"过闸后还剩几条"。
> 两者差一个数量级：同一批 60 题，无闸门 83.3%，0.76 精排闸门 23.3%。
> 本文第一步把口径统一，第二步把"分解只挂在精排分支"这个结构缺陷修掉。

## 1. 第一步：把闸门接进评测

`tools/evaluate_gated_retrieval.py`：三种打分方式 × 两种查询组织方式，一次跑完。

| 打分方式 | 含义 |
|---|---|
| `none` | 不设闸门（历史评测口径，作上界参考） |
| `cosine 0.53` | 线上默认链路 |
| `rerank 0.76` | 精排链路（bge-reranker-v2-m3，本地权重 + GPU） |

**双口径输出**（关键）：

- `full(片段)`：`passed[:feed_topk]` 截断片段——**生产真实行为**（同一篇文档可能占满 3 条）
- `full(文档)`：先按文档去重再取 top-K——历史评测口径（`0.76 闸门 23.3%` 就是这个）

不区分这两个，就会拿宽松口径当线上表现。实测差距：cosine 下 76.7% vs 81.7%，差 5pp。

## 2. 结果

60 条耦合问句（A40/B10/C6/D4）+ 8 条无答案题：

| 条件 | full(片段) | full(文档) | coverage | 无答案误接受 |
|---|---|---|---|---|
| none / off | 83.3% | 90.0% | 92.8% | 100% |
| none / on | 88.3% | 98.3% | 95.0% | 100% |
| **cosine / off（线上默认）** | **76.7%** | 81.7% | 88.9% | **75%** |
| **cosine / on（本次改动）** | **85.0%** | 90.0% | 93.3% | 75% |
| **rerank / off** | **23.3%** | 23.3% | 39.7% | **0%** |
| **rerank / on** | **60.0%** | 60.0% | 76.7% | 0% |

- `rerank` 两行与历史记录 **23.3% / 60.0% 逐位相同**，说明这套评测与项目原有口径已对齐。
- 延迟：rerank 6 个候选在 GPU 上 **260ms/问**（历史 CPU 是 4.8s）；检索耗时是内存点积，不代表 Chroma 真实开销。

## 3. 结论

1. **默认链路的短板是拒答，不是召回**：full 76.7% 尚可，但 8 条无答案题有 **6 条被放行**（75%）。
   这是个产品级问题——用户问库外的问题，系统会拿不相关片段硬答。
2. **精排治拒答，但代价是召回崩**：23.3% full、0% 误接受。两者不可兼得，除非配分解。
3. **分解在两条链路上都有收益，精排下收益最大**：
   - cosine：76.7% → **85.0%**（+8.3pp）
   - rerank：23.3% → **60.0%**（+36.7pp）
   - 无闸门：83.3% → 88.3%（+5pp）
4. **闸门会误杀正确片段**：无闸门 83.3% → cosine 0.53 后 76.7%，掉 6.6pp。
   这 6.6pp 全是"分数不够但确实正确"的片段，说明 0.53 对多文档题偏严。
5. **`rerank + 分解` 是唯一"双高"组合**（60% full / 0% 误接受），也是历史记录里推荐的方向。

## 4. 第二步：分解从精排分支提到检索入口

改动前：`query_decompose.decompose()` 只在 `_rerank_passed()` 里调用，而 `RAG_RERANK_ENABLED` 默认 false
→ **复合问句在默认配置下从未被拆过**。

改动后（`rag_service.search()`）：

```python
if not rerank_requested:                     # 默认 cosine 链路
    subs = query_decompose.decompose(query)  # 开关关闭时直接返回 [query]，零额外开销
    if len(subs) > 1:
        return self._multi_query_cosine(db, subs, candidate_k, feed_topk, timing)
```

`_multi_query_cosine()`：每个子句各自召回 → 过 0.53 闸门（保留型号逐字命中豁免）→
按 `(doc_id, chunk)` 取最高分合并 → 排序截断。与精排分支的合并语义一致，只是打分用 cosine。

单主题问题（`decompose` 返回 `[query]`）仍走原路径，不改变阈值标定尺度。

**验证**：`tools/verify_decompose_entry.py` 用真实 `RAGService.search()`（检索层替换为内存向量）跑出
`off 76.7% / on 85.0%`，与评测脚本的 cosine 档**逐位一致**——说明评测口径与生产实现没有分叉。

## 5. 复现

```bash
cd llmops-backend
# 三档打分 × 两种组织（需要 Ollama bge-m3 + 本地 reranker 权重）
.venv/Scripts/python.exe tools/evaluate_gated_retrieval.py
# 生产代码路径校验（不需要 Chroma/MySQL）
.venv/Scripts/python.exe tools/verify_decompose_entry.py
```

## 6. 局限

- 检索耗时是内存点积，不含 Chroma 与在线 embedding 的真实开销；rerank 是 GPU 数，CPU 会慢一个量级。
- 语料 11 篇 / 21 片段，C 型只有 6 题，分形态结论不稳。
- `none` 档的"拒答失败 100%"是必然的（没有闸门），只作对照。
- 分解用的子句来自 `decompose_cache.jsonl`（老师产出），学生模型的版本见 docs/10；
  生产上启用需把 `RAG_QUERY_DECOMPOSE_ENABLED` 打开，并承担每问一次 LLM 调用的成本。
