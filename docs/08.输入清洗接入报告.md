# 输入清洗接入报告

> 目标：把「用户随手粘贴的脏文本」在进检索之前规范化，避免噪声污染 bge-m3 向量、
> 以及全角字符让「精确编号豁免」失效。清洗能力来自一个蒸馏出来的 0.8B 小模型
> （[Qwen3.5-0.8B-TextPreprocessor](https://github.com/wj239951/Qwen3.5-0.8B-TextPreprocessor)），
> 同时提供一份零依赖的规则实现作为默认通道。

## 1. 为什么 RAG 需要这一层

真实输入不是评测题里那种干净问句。复制粘贴会带进来：

| 噪声 | 对 RAG 的具体伤害 |
|---|---|
| 零宽字符 / BOM | 分词后出现不可见 token，`ZX-2026` 变成 `ZX-2026`，"精确编号逐字命中"直接失效 |
| 全角字母数字 | `ＺＸ－２０２６` 与库里的 `ZX-2026` 字面不同，BM25 与精确豁免都匹配不上 |
| 连续重复字 | `我我我 想 问问问` 让查询向量偏向"我"这个高频字，语义重心偏移 |
| HTML 残留 | 从网页复制会带 `<p>`、`&nbsp;`，`&nbsp;` 进入查询后是一个独立 token |
| PDF 硬换行 | 一句话被折成三行，查询变成三个片段，向量被平均掉 |

这五类里，前四类**不需要模型**——它们是确定性的字符变换，用代码做既准又快。
这也是本项目把清洗拆成两条通道的原因。

## 2. 架构：两条通道 + 统一降级

```
用户输入 ──► InputCleaner ──┬─ rule  ：进程内纯标准库，0.06–0.74 ms
                            ├─ model ：HTTP 调 tools/clean_server.py（0.8B 蒸馏模型）
                            └─ off   ：原样透传
                                   │
                          失败时按 INPUT_CLEAN_FALLBACK 回退（rule / off）
                                   ▼
                     清洗后文本 → 检索（use_rerank 不变）→ 拼上下文 → 生成
```

- **用户原文仍然入库**：`chat_logs.user_input` 存的是用户输入的原样文本，清洗结果只用于
  检索与提问。这样日志/历史消息里看到的是用户真的说了什么，排查问题不会被"洗过的问句"误导。
- **失败不回传异常**：模型通道超时/未启动时记一条 warning 并按配置回退，主链路不受影响
  （与精排"不可用就回退 cosine"是同一套语义）。
- **请求级开关**：`use_clean` 可覆盖服务端配置，前端「输入清洗」开关就用它；
  `use_clean_model` 进一步把**本次请求**升级到模型通道（见 §7）。
- **超长不算**：超过 `INPUT_CLEAN_MAX_CHARS`（默认 4000）直接跳过，避免模型通道拖慢首字。

## 3. 实测

环境：RTX 4060 8GB，模型 fp16 常驻显存约 1.6GB，单卡串行。

### 3.1 耗时

| 通道 | 单次耗时 | 说明 |
|---|---|---|
| `rule` | **0.06–0.74 ms** | 纯字符串处理，无 I/O |
| `model` | **p50 393 ms / p95 600 ms / max 676 ms** | GPU 已预热；冷启动首次约 2–3 s |

模型通道的 0.4 s 会直接加到首字延迟上。对话场景里这属于"能感觉到但可接受"的量级，
所以默认不用它。

### 3.2 在真实评测题上的表现

拿 `experiments/eval_qa.jsonl` 的 45 条题测：

- **模型与规则输出 100% 一致（45/45）**——因为这些题本身就是干净手写问句，两者都判定"不用改"。
  这说明**清洗对现有基线是 no-op**，不会把已有指标搞坏，但也别指望它提升现有分数。

### 3.3 脏化实验：还原能力

把 45 条题分别注入 5 类噪声，再用两条通道清洗，看能否还原成干净版本：

| 噪声类型 | 规则还原率 | 模型还原率 |
|---|---|---|
| 零宽字符 | **100%** | 87% |
| 全角化 | **100%** | 93% |
| HTML 包裹 | **100%** | 96% |
| 重复字符 | **100%** | 96% |
| 空格污染 | **100%** | 98% |

结论很反直觉但很明确：**在机械噪声上规则全面优于 0.8B 模型**。原因是这类变换是确定性
字符映射，规则不可能错；模型是学出来的，在短句上偶有漏改（87–98%）。

那模型的价值在哪？在规则做不了的**判断**上：

- 段落里哪几行是"排版折断"该合并、哪几行是本来就要分行（列表、标题）；
- 中英混排时哪里该保留空格；
- 一段文本整体是"脏"还是"本来就干净"——规则只会机械执行，模型会整体判断。

所以默认 `rule`，`model` 作为可选增强，专门给"长段落 / PDF 粘贴"这类场景用。

## 4. 怎么开

```dotenv
# 默认方案：规则清洗，零依赖
INPUT_CLEAN_MODE=rule
INPUT_CLEAN_FALLBACK=rule
```

```powershell
# 增强方案：另起清洗服务（需要 GPU / 4GB+ 内存）
pip install -r requirements-clean.txt
python tools/clean_server.py --model <Qwen3.5-0.8B-TextPreprocessor 目录> --port 8010
```

```dotenv
INPUT_CLEAN_MODE=model
INPUT_CLEAN_SERVER_URL=http://127.0.0.1:8010
INPUT_CLEAN_FALLBACK=rule   # 服务没起来也不影响问答
```

响应里会带清洗元信息，前端据此显示"输入已清洗"：

```json
"clean": {"mode": "rule", "applied": true, "changed": true,
          "fallback": null, "reason": null, "ms": 3,
          "clean_query": "ZX-2026 的额定压力是多少"}
```

## 5. 已知边界

- **模型通道不修乱码**：蒸馏出的 0.8B 模型没有这个能力（训练时刻意剔除了乱码样本，
  否则小模型会靠背文本蒙混、在真实输入上凭空编造）。乱码还原在 `clean_server.py`
  里用确定性代码先做掉，与规则通道行为一致。
- **模型通道要求常驻进程**：2 核 2G 云服务器装不下 1.6GB 权重的 torch 进程，
  该环境下只能用 `rule`（或 `off`）。这与精排的取舍完全一致。
- **清洗不能救"问得不对"**：它只修字符，不做同义改写。`ZX-2026` 写成 `ZX2026`
  仍然要靠混合检索的关键词通道兜底。
- **端到端检索指标见 [docs/09](09.输入清洗检索评测报告.md)**：把 75 条题弄脏后重测，
  清洗把短查询的 hit@3 从 73.3% 拉回 86.7%、MRR 从 0.606 拉回 0.689（与干净基线一致）；
  长句四种条件下全是 100%，说明 bge-m3 对轻度噪声本来就鲁棒——这也解释了本报告 §3.2
  "在干净评测题上两者输出一致"的现象。

## 7. 请求级双通道（2026-11-17 增补）

### 7.1 为什么要按请求选通道

规则通道是毫秒级、确定性的，适合当主链路默认；模型通道判断力更强，但一次要几百毫秒到
一两秒，**不该每次都跑**。原来的开关只是"总开关"（`use_clean` 只能开或关），通道由服务端
`INPUT_CLEAN_MODE` 一刀切，等于让所有人共用同一个取舍。

现在拆成两级，语义互不越权：

| 开关 | 作用域 | 语义 |
|---|---|---|
| `use_clean` | 请求 | 本次要不要清洗；`false` 是更强的"不要"，能压过通道开关 |
| `use_clean_model` | 请求 | 本次要不要**升级到模型通道**（精细清洗） |
| `INPUT_CLEAN_MODE` | 服务端 | 默认通道（建议 `rule`） |
| `INPUT_CLEAN_MODEL_ALLOWED` | 服务端 | 是否允许请求级升级；`false` 时按钮隐藏、请求里的 `true` 被忽略 |

**默认行为没变**：`.env` 里 `INPUT_CLEAN_MODE=rule` 时主链路依旧是规则清洗，只有前端显式
点「精细清洗」的那一次才走模型。

不升级时都不报错，而是记进 `clean.fallback_reason`：

- `not_allowed`：服务端 `INPUT_CLEAN_MODEL_ALLOWED=false`（2 核 2G 机器就该这么配）
- `error`：模型服务没起、超时、返回格式不对（按 `INPUT_CLEAN_FALLBACK` 回退规则）

前端据此把提示分成两句——「服务端未允许精细清洗」和「模型通道不可用」，因为用户的处理
动作不一样：前者找管理员，后者重启 sidecar。

### 7.2 GPU 实测（RTX 4050 Laptop 6GB）

模型通道原先在 CPU 上 17–31 s/次，实际上等于不可用。换成 CUDA 版 torch 后：

| 环节 | 耗时 |
|---|---|
| 模型加载（首次，含 CUDA 初始化） | 7.5 s |
| 黄金用例 5 条（`tools/verify_release.py` 的那组） | 0.4 – 1.5 s |
| HTTP 端到端（后端 `InputCleaner` → sidecar） | 0.63 / 0.69 / 1.25 s |
| 常驻显存 | 3.6 GB / 6.1 GB |

对照 §3 的 p50 393 ms，回到同一量级。

**环境约束**：驱动 566.24 只支持到 CUDA 12.7，所以能用的最高通道是 **cu126**
（`torch==2.14.1+cu126`）；cu128 要 12.8+ 驱动、cu132 要 13.x，都装不上。
装完 `pytest` 仍 104 passed，说明降一个 minor 对现有功能无影响。

### 7.3 新发现的失败模式（重要）

GPU 化之后拿真实脏文本压测，发现模型通道**不是严格优于规则通道**：

| 输入 | 模型通道 | 规则通道 |
|---|---|---|
| `你好…，这这这是 测试！！！ <b>粗体</b> Ｈｅｌｌｏ` | `你好，这是 测试！ Hello`（**"粗体"整段丢失**） | `…测试！粗体 Hello`（保留正文，只删标签） |
| `你好，这是 测试！！！ <b>粗体</b>` | `你好，这是 测试！ <b>粗体</b>`（**标签没删干净**） | 标签正确删除 |

- 短输入单独测 6 条，标签内正文都保留正确；**正文丢失只在多种噪声叠加的长输入上复现**。
- 标签残留是另一类问题：模型有时只做标点规整、跳过 HTML 剥离。

结论：模型通道的价值在"语义级判断"（`我我我` 该不该压、断行该不该接），但**内容保真与
标签剥离不如确定性规则可靠**。这正是"默认 `rule`、模型通道只做显式可选"的设计前提。
建议在模型卡的「已知限制」里补一条"极小概率吞掉标签内正文"——那是它自己的评测集
（漏删率 / 新增率）覆盖不到的维度。
