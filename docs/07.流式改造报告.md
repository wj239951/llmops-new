# 流式对话改造报告（SSE 增量输出）

> 对应代码：`llmops-backend/app/api/chat.py`、`app/services/chat_service.py`、`app/services/llm_service.py`、`app/services/deepseek_service.py`、`app/services/ollama_service.py`；`llmops-frontend/src/api/chat.ts`、`src/types.ts`、`src/views/ChatStudio.vue`
> 对应接口：`POST /api/chat/stream`（`text/event-stream`）；旧 `POST /api/chat` 保留为非流式回退
> 对应测试：`llmops-backend/tests/test_chat_stream.py`（5 条）；后端全量 33 passed，前端 `vue-tsc` / `vite build` 通过
> 关联文档：[docs/04.评测报告](04.评测报告.md)、[docs/05.Rerank实验报告](05.Rerank实验报告.md)、[docs/06.混合检索实验报告](06.混合检索实验报告.md)

## 1. 背景：为什么非流式体验不够

改造前，对话只有一条路径：前端 `POST /api/chat`，后端走完 Prompt 解析 → 会话记忆 → RAG 检索 → 模型生成 → 写调用日志，最后一次性返回 `ChatResponse`。在生成长回答时，页面只能显示一个 loading 动画，用户看不到任何中间状态：

- **首字等待被放大**：本地 `deepseek-r1:7b` 在 CPU 上生成较慢，开 RAG 精排时检索本身还要数秒（见 [docs/05](05.Rerank实验报告.md) 的 CPU 精排代价），这段时间前端完全空白；
- **思维链只能最后看**：`deepseek-reasoner` 的 `reasoning_content`、Ollama 的 `thinking` 本来是按 token 产生的，非流式接口却把它们憋到全部结束才一起返回；
- **RAG 阶段不可见**：用户不知道这次请求是在检索、在推理、还是在生成，也不知道命中了哪些知识片段；
- **失败反馈滞后**：模型调用中途失败时，前端只能收到一个整体错误，已经生成的部分内容直接丢失。

因此本次改造的目标是：

1. **首包先行**：请求后尽快出现「准备 / 检索 / 生成」状态，而不是长时间空白；
2. **增量渲染**：`reasoning` 与回答正文分别作为追加流实时展示；
3. **RAG 前置可见**：在生成开始前推送 `meta`，把模型、`rag_status` 与 `sources` 先交给前端；
4. **失败可见、可收尾**：流内用 `error` 事件报错，服务端把已生成的部分答案写入失败日志；
5. **不破坏旧接口**：`POST /api/chat` 原样保留，作为未更新客户端与流式失败时的回退路径。

本文只讲「对话链路怎么从一次性响应改成 SSE 流式」；检索质量与阈值标定见 docs/04–06。时延类数据（TTFT、总耗时）与环境强相关，本文在 7.4 记录一次本地联调的实测值并标注环境，不把它们当作通用性能指标。

## 2. 方案对比：MVP 伪流式 vs 全链路 SSE

落地前对比过两条路径。

**方案 A（MVP）：前端打字机伪流式。** 后端完全不动，仍然一次性返回完整 `answer`；前端拿到全文后用定时器逐字渲染，制造「正在打字」的观感。

**方案 B（采纳）：后端 SSE + 前端增量渲染。** 后端新增 `POST /api/chat/stream`，用 `StreamingResponse` 生成器把状态、元信息、`reasoning` 分片、回答分片、汇总依次下发；前端用 `fetch` + `ReadableStream` 逐帧解析并增量更新界面，非流式接口保留。

| 维度 | 方案 A：前端打字机（MVP） | 方案 B：SSE 全链路（采纳） |
| --- | --- | --- |
| 首字可见时间 | 不变——仍要等整段生成完才开始「打字」 | 首个分片到达即可见 |
| 长回答过程 | 无法感知进度 | 回答卡片实时增长 |
| 思维链 | 随整段响应到达后一次性展示 | `reasoning` 分片独立推送、实时展示 |
| RAG 阶段与来源 | 不可见，只能等最终 `sources` | `meta` 在生成前推送 `rag_status` 与 `sources` |
| 中途失败 | 整段失败，无部分结果 | 流内 `error` 报错，已生成部分落失败日志 |
| 后端改动 | 无 | 新增 1 个端点、1 个事件生成器、两个 provider 的 `chat_stream` |
| 前端改动 | 只改 `ChatStudio.vue` | `api/chat.ts` 新增流式客户端、`types.ts` 新增类型、页面改增量状态机 |
| 代理要求 | 无 | 响应不能被中间层缓冲（SSE 头 + 反代配置） |
| 回滚成本 | —— | 旧端点保留，前端切回 `sendChat` 即可 |

选择 B 的理由：

- A 只改变**观感**，不改变**等待**；首字时间（TTFT）与总耗时一个都不降，长回答时「假装流式」甚至会让用户多等一轮打字动画；
- B 的交互收益来自传输层本身，且现有 `ChatService` 已经把 Prompt / 记忆 / RAG / 日志串好了，流式改造是**复用同一条链路换一种输出方式**，不是另写一套对话逻辑；
- B 的风险用旧接口兜住：前端在「首包前失败」时自动降级 `POST /api/chat`（见 5.4），旧端点因此既是兼容层，也是安全网。

## 3. 协议设计

### 3.1 端点与请求

流式接口与旧接口共享同一套请求模型：

- 路径：`POST /api/chat/stream`
- 鉴权：与 `/api/*` 一致，请求头 `Authorization: Bearer <DEMO_PASSWORD>`；
- 请求体：与 `ChatRequest` 完全一致（`query`、`prompt_id`、`system_prompt`、`model_provider`、`model_name`、`temperature`、`top_p`、`use_rag`、`conversation_id`、`memory_enabled`）。

```
POST /api/chat/stream HTTP/1.1
Authorization: Bearer demo2026
Content-Type: application/json

{"query":"注塑机 ZX-2026 的螺杆传动链条必须使用什么型号的润滑脂？","use_rag":true,"model_provider":"ollama","model_name":"deepseek-r1:7b","temperature":0.2}
```

选择 SSE 而不是 WebSocket 的原因：对话是**单向**推送，不需要双向信道；SSE 直接复用 HTTP 鉴权、CORS 与现有的路由依赖，不需要额外的连接管理或心跳协议。选择 `POST` 而不是 `EventSource` 的原因：`EventSource` 只支持 GET，查询体要放在 URL 里既不适合长问题也不安全，所以前端用 `fetch` + `ReadableStream` 自己解析 SSE 帧。

### 3.2 响应头与帧格式

成功时返回 `200`，`Content-Type: text/event-stream`，并附带三个反缓冲头：

| 响应头 | 值 | 作用 |
| --- | --- | --- |
| `Cache-Control` | `no-cache` | 禁止浏览器/代理缓存半截响应 |
| `Connection` | `keep-alive` | 保持长连接 |
| `X-Accel-Buffering` | `no` | 让 nginx 等反向代理不要缓冲；Caddy 默认逐块转发 |

每个事件是一个标准 SSE 帧，`data` 为 JSON（`ensure_ascii=False`，中文原样输出）：

```
event: <事件名>
data: <JSON>

```

帧与帧之间用空行分隔。前端按 `\n\n` 分帧，而不是按单行读取——TCP 分片不保证一次 `read()` 恰好对应一个事件。

### 3.3 事件表

| 事件 | `data` 字段 | 次数 | 说明 |
| --- | --- | --- | --- |
| `status` | `phase`: `preparing` / `retrieving` / `generating` | 1–3 | 阶段提示；`retrieving` 仅在 `use_rag=true` 时出现 |
| `meta` | `conversation_id`、`model_provider`、`model_name`、`prompt_name`、`rag_status`、`sources` | 1 | 生成前下发；`sources` 元素为 `{title, snippet, source, score}`，`snippet` 截前 200 字 |
| `reasoning` | `delta`（字符串） | 0–n | 思维链增量；`deepseek-reasoner` 的 `reasoning_content`、Ollama 的 `thinking` 分片 |
| `delta` | `content`（字符串） | 0–n | 回答正文增量 |
| `done` | `answer`、`reasoning`、`thought`、`model_provider`、`model_name`、`total_tokens`、`latency_ms`、`first_token_ms`、`conversation_id`、`prompt_name`、`rag_status`、`sources` | 1 | 终态汇总，前端以它覆盖增量累计结果 |
| `error` | `message`、`latency_ms` | 0–1 | 终态错误；异常时取代 `done` |

### 3.4 事件顺序

```
客户端 POST /api/chat/stream
        │
        ▼
 status{preparing} ──► 解析 Prompt / 加载会话记忆
        │
        ├─ use_rag=true ──► status{retrieving} ──► RAG 检索（可能含精排）
        │
        ▼
 meta{conversation_id, model_provider, model_name, prompt_name, rag_status, sources}
        │
        ▼
 status{generating} ──► 调用 provider 流式接口
        │
        ├─ reasoning{delta} × n   （reasoner / ollama thinking，可能没有）
        ├─ delta{content} × n     （回答正文）
        │
        ▼
 done{answer, reasoning, thought, total_tokens, latency_ms, first_token_ms, ...}

任一步抛出异常 ──► error{message, latency_ms}（不再发 done）
```

### 3.5 示例报文

以下为一次启用 RAG 的流式请求的帧结构示例（`sources` 的分数与截断内容为示例值，具体随语料变化）：

```
event: status
data: {"phase": "preparing"}

event: status
data: {"phase": "retrieving"}

event: meta
data: {"conversation_id": null, "model_provider": "ollama", "model_name": "deepseek-r1:7b", "prompt_name": null, "rag_status": "hit", "sources": [{"title": "注塑机润滑与保养", "snippet": "……螺杆传动链条应使用 RL-2077 润滑脂……", "source": "mysql-init/llmops_db.sql", "score": 0.61}]}

event: status
data: {"phase": "generating"}

event: reasoning
data: {"delta": "用户问的是注塑机螺杆传动链条的润滑脂型号……"}

event: delta
data: {"content": "根据知识库，"}

event: delta
data: {"content": "螺杆传动链条应使用 RL-2077 润滑脂。"}

```

`done` 帧的结构见 3.3；首字时间与总耗时随机器、模型与是否开 RAG 变化，一次本地联调的实测值见 7.4。

### 3.6 语义约定

- `reasoning` / `delta` 是**增量**，客户端必须追加，不能覆盖；同一帧里只会出现一种增量；
- `done` 是**权威汇总**：前端收到后以 `done` 的字段覆盖本地累计值，既用于补齐 `thought`、`total_tokens`、`first_token_ms`，也能消除分帧/重复渲染带来的偏差；
- `meta` 在生成前发出，前端可以先把「用了哪个模型、是否命中知识库、命中哪些片段」渲染出来；
- `rag_status` 沿用四态：`off`（未启用 RAG）、`no_hit`（启用但无过阈值片段）、`weak_hit`（top1 勉强过线，不可当可靠依据）、`hit`（正常命中）；
- `first_token_ms` 的口径是「从进入 `stream()` 到第一个 `reasoning` 或 `delta` 分片到达」的毫秒数，只记一次；空回答时为 `null`；
- `latency_ms` 是「从进入 `stream()` 到 `done` / `error`」的毫秒数，包含 Prompt 解析、会话记忆、RAG 检索、生成与日志落库；
- `total_tokens`：DeepSeek 取最后一个 usage 分片的 `total_tokens`；Ollama 取 `prompt_eval_count + eval_count`；上游不返回 usage 时为 0。

### 4.2 接口层：`_sse()` 与 `StreamingResponse`

```python
SSE_HEADERS = {
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",
}

def _sse(item: dict) -> str:
    """把事件字典序列化为 SSE 帧。"""
    data = json.dumps(item.get("data") or {}, ensure_ascii=False)
    return f"event: {item.get('event', 'message')}\ndata: {data}\n\n"

@router.post("/stream")
def chat_stream(req: ChatRequest, db: Session = Depends(get_db)):
    def event_source():
        try:
            for item in service.stream(db, req):
                yield _sse(item)
        except Exception as exc:  # 生成器内部已兜底，这里再防一层，避免连接裸断
            yield _sse({"event": "error", "data": {"message": str(exc)}})

    return StreamingResponse(event_source(), media_type="text/event-stream", headers=SSE_HEADERS)
```

两个要点：

- **业务层产出字典，接口层负责序列化**。`ChatService.stream()` 只 `yield {"event": ..., "data": ...}`，不关心 SSE 文本格式，测试因此可以直接断言事件名与 `data`，不必解析字符串；
- **两层兜底**。`ChatService.stream()` 内部已用 `try/except` 发 `error`，接口层再包一层：万一生成器在发事件之外的位置抛异常，也把它转成一条 `error` 帧，而不是让连接直接断开。

### 4.3 生成器：`ChatService.stream(db, req)`

生成器按下面的顺序产出事件（与 3.4 一致）：

1. `status{preparing}`：先给前端一个立即可见的状态，再进入耗时准备工作；
2. `_prepare(db, req)`：解析 Prompt（`prompt_id` 存在时覆盖 `system_prompt` / provider / model / 温度 / top_p）、解析默认模型名、按 `memory_enabled + conversation_id` 加载最近 `MEMORY_MAX_TURNS` 轮成功对话；
3. `use_rag=true` 时发 `status{retrieving}`，然后 `_apply_rag()`：检索 → 阈值过滤 → 拼 `final_query` → 判定 `rag_status`；
4. `meta`：`conversation_id`、实际 provider/model、`prompt_name`、`rag_status`、`sources`；
5. `status{generating}`，调用 `LLMService.chat_stream(...)`，对每个分片转发 `reasoning` / `delta`；
6. 汇总 `answer` / `reasoning` / token / 时延 → 写成功 `ChatLog` → `done`。

与非流式 `chat()` 的关系：两条路径共用 `_prepare()` 与 `_apply_rag()`，Prompt 解析、会话记忆、RAG 判定、`sources` 截断（`content[:200]`）都只有一份实现，避免「非流式改了、流式忘了改」的漂移。

几个容易踩的实现细节：

- **汇总分片不能当增量发**：provider 的最后一个分片带 `{"done": True, "answer": ..., "reasoning": ...}`，如果循环不先判断 `chunk.get("done")`，汇总文本会被当成增量重复推送一遍（`test_stream_event_order_and_meta` 断言的事件序列里会多出 `reasoning`/`delta`）。正确做法是先缓存汇总、`continue`，循环结束后统一发 `done`；
- **`first_token_ms` 只记一次**：第一个 `reasoning` 或 `content` 分片到达时记时间，后续分片不覆盖；
- **本地拼接是兜底**：`answer`、`reasoning` 优先取 provider 汇总分片，没有汇总时用本地分片拼接；Ollama 的思维链若被内联进回答，最后由 `_split_reasoning_and_answer()` 剥离；
- **写日志在 `done` 之前**：成功日志的 `latency_ms` 已包含落库前的耗时；失败分支把 `"".join(answer_parts)` 作为部分答案写入 `assistant_output`，并记 `error_message`；
- **`finally` 关闭模型流**：无论正常结束、异常还是客户端取消，都调用 `model_stream.close()` 释放上游 HTTP 连接。

### 4.4 双 provider 流式

**DeepSeek**

- 用 OpenAI SDK：`client.chat.completions.create(..., stream=True, stream_options={"include_usage": True}, timeout=100)`；
- `delta.reasoning_content` → `reasoning` 分片（`deepseek-reasoner` 有，`deepseek-chat` 没有）；`delta.content` → 正文分片；
- 最后一个 chunk 可能 `choices` 为空但带 `usage`，循环里单独取 `usage.total_tokens`；
- 流结束后产出 `{"done": True, "answer", "reasoning", "model_provider": "deepseek", "model_name", "total_tokens"}`；
- `DEEPSEEK_API_KEY` 未配置时抛 `ValueError`，由 `stream()` 的异常分支转成 `error` 事件。

**Ollama**

- 走原生 `POST {OLLAMA_BASE_URL}/api/generate`，`stream: True`，`timeout=(10, 180)`（连接 10s / 读 180s）；
- 返回是 **NDJSON**（每行一个 JSON，不是 SSE），用 `response.iter_lines(decode_unicode=True)` 逐行解析；
- `data["thinking"]` → `reasoning` 分片（新版 Ollama 的思考字段）；`data["response"]` → 正文分片；
- `data["done"]` 时取 `prompt_eval_count` / `eval_count`，退出循环；
- 结束后用 `_split_reasoning_and_answer()` 剥离正文里内联的 `<think>…</think>`；若没有 `thinking` 分片，则把剥离出的内联内容作为 `reasoning` 回退；
- `session.trust_env = False`：避免系统代理环境变量把 `127.0.0.1:11434` 的请求带偏。

### 4.5 日志与 TTFT

流式请求的落库与非流式一致，只是写入时机改成「流结束前」：

- 成功：`ChatLog(status="success", assistant_output=answer, total_tokens, latency_ms=总耗时)`，并维护会话标题/更新时间；
- 失败：`ChatLog(status="failed", assistant_output=已生成部分, total_tokens=0, latency_ms, error_message=str(exc))`；
- 日志行：`chat.stream done provider=%s model=%s ttft_ms=%s latency_ms=%s tokens=%s`。

时延拆成两个口径，避免「只知道总耗时、不知道慢在首字还是慢在长尾」：

| 指标 | 位置 | 口径 |
| --- | --- | --- |
| `first_token_ms`（日志 `ttft_ms`） | `done.first_token_ms` | 从进入 `stream()` 到第一个 `reasoning` / `delta` 分片的毫秒数；无分片为 `null` |
| `latency_ms` | `done.latency_ms` / 日志 | 从进入 `stream()` 到 `done` / `error` 的总毫秒数，含检索、生成、落库 |

TTFT 和总耗时随机器、模型大小、是否开 RAG 精排变化很大；本文只固定口径，具体数值放 7.4 并标注环境，方便后续在同一口径下对比。

### 4.6 异常、取消与降级

- **业务异常**：生成器整体包在 `try/except Exception` 中，`logger.exception` + 写失败日志 + `yield error`；`error.data` 带 `message` 与 `latency_ms`；
- **接口层兜底**：见 4.2，防止异常发生在事件生成之外时连接裸断；
- **客户端主动取消**：用户点「取消」时前端 `AbortController.abort()`，Starlette 取消请求任务，生成器收到 `GeneratorExit`（不是 `Exception` 子类），因此**不会**发 `error`、也不会写成功/失败日志；尚未关闭的模型流由 `finally` 释放；
- **首包前失败降级**：由前端负责（见 5.4）。后端不自动重试——旧 `POST /api/chat` 保留，重试策略放在离用户最近的一层；
- **兼容**：请求模型 `ChatRequest` 不动、旧接口响应模型 `ChatResponse` 不动、数据库无 schema 变更、无新增依赖（`requests`、`openai` 原本就在）。

## 5. 前端实现

### 5.1 API 层：`sendChatStream`

浏览器端不能用 axios 读流式响应（XHR 不支持增量读取响应体），因此单独用 `fetch` + `ReadableStream` 实现，`sendChat` 原样保留：

```ts
// src/api/chat.ts
export type ChatStreamPhase = 'preparing' | 'retrieving' | 'generating'

export interface ChatStreamHandlers {
  onStatus?: (phase: ChatStreamPhase) => void
  onMeta?: (meta: ChatStreamMeta) => void
  onReasoning?: (delta: string) => void
  onDelta?: (content: string) => void
  onDone?: (done: ChatStreamDone) => void
  onError?: (message: string) => void
}

export async function sendChatStream(
  payload: ChatRequestPayload,
  handlers: ChatStreamHandlers,
  signal?: AbortSignal,
): Promise<void>
```

实现要点：

- **URL 与请求头**：`${import.meta.env.VITE_API_BASE_URL}/chat/stream`，`Content-Type: application/json`、`Accept: text/event-stream`，`Authorization: Bearer <localStorage 中的 token>`（与 `request.ts` 的请求拦截器同一来源）；
- **401 处理**：`response.status === 401` 时与 axios 拦截器保持一致——清 token + `location.reload()`，避免两个客户端对登录态的处理分叉；
- **非 2xx**：抛 `流式请求失败：HTTP <status>`；响应没有可读 `body` 时也直接抛错，交给页面的降级/提示逻辑；
- **分帧解析**：`response.body.getReader()` + `TextDecoder` 循环读取；`decoder.decode(value, { stream: true })` 处理跨块的多字节字符；先把 `\r\n` 归一化成 `\n`，再按 `\n\n` 切帧（保留最后一个不完整片段），处理「一个事件跨多次 `read()`」和「一次 `read()` 含多个事件」；帧内解析 `event:` 与 `data:` 行（`data:` 后仅去掉一个前导空格，多行用 `\n` 拼接），`JSON.parse` 后按事件名分发到 handlers；
- **容错**：`data` 不是合法 JSON 时保留原始文本继续处理，不中断整条流；未知事件名直接忽略，方便后端以后加事件而不破坏旧前端；
- **收尾**：流结束后再 `decoder.decode()` flush，把缓冲里的最后一帧按同样规则解析；`AbortError` 直接抛给页面识别，不弹全局错误；`reader.releaseLock()` 放在 `finally` 里。

把手柄（handlers）放在 API 层、页面只做状态更新，是为了让 SSE 解析逻辑可复用、可单测，也避免把分帧细节散落在模板代码里。

### 5.2 类型定义

`types.ts` 追加两个类型，复用已有的 `Source` / `RagStatus`；`ChatResponse` 不动（旧接口契约不变）：

```ts
export interface ChatStreamMeta {
  conversation_id: string | null
  model_provider: string
  model_name: string
  prompt_name: string | null
  rag_status: RagStatus
  sources: Source[]
}

export interface ChatStreamDone {
  answer: string
  reasoning: string | null
  thought: string
  model_provider: string
  model_name: string
  total_tokens: number
  latency_ms: number
  first_token_ms: number
  conversation_id: string | null
  prompt_name: string | null
  rag_status: RagStatus
  sources: Source[]
}
```

注：`first_token_ms` 在类型里按 `number` 声明；后端空回答时可能下发 `null`，前端目前不展示该字段，接指标面板时需要把两者收敛一致。

### 5.3 `ChatStudio.vue` 增量渲染

页面从「一次 `await` 后整体赋值」改成「一个事件驱动的状态机」：

- 新增 `streamPhase`（`正在准备` / `正在检索知识库` / `正在生成…`），在按钮附近用 `el-alert` 展示；
- `submit()` 先清空上一轮的 `answer` / `reasoning` / `sources` / `rag_status`，创建 `AbortController`，然后调用 `sendChatStream`：
  - `onStatus` → 更新 `streamPhase`；
  - `onMeta` → 更新 `conversation_id`、模型信息、`sources`、`rag_status`；
  - `onReasoning` → `reasoning += delta`，思考过程卡片实时增长；
  - `onDelta` → `answer += content`，最终回答卡片实时增长；
  - `onDone` → 用最终值覆盖 `answer` / `reasoning` / `thought` / `total_tokens` / `latency_ms` / `rag_status` / `sources` / `conversation_id`；
  - `onError` → `ElMessage.error` 提示，保留已生成的部分内容；
- 取消按钮继续复用现有 `loading` 状态，`cancel()` 改为 `AbortController.abort()`；捕获到 `AbortError` 视为用户主动取消，不报错；
- `finally` 恢复 `loading` 与按钮态。

模板无需重写：原有「思考过程」「最终回答」「来源」卡片都绑在响应式变量上，增量更新自然生效。

### 5.4 首包前失败自动降级

流式链路比一次性请求多出「连接建立、帧解析、代理转发」几个失败点。页面按**是否已经看到实质输出**区分处理：

- **收到任何 `reasoning` / `delta` 之前失败**（网络错误、非 401 的 HTTP 错误、没收到任何事件流）→ 自动调用原有的 `sendChat` 非流式接口重试一次，并提示「流式输出不可用，已自动降级为非流式请求」；
- **已经渲染出部分内容后失败** → 不降级，避免同一问题生成两遍、日志写两条；只提示错误并保留已显示内容；如果流没有 `done` 就断开，额外提示「流式输出中断，回答可能不完整」；
- **401 不降级** → 交给统一登录处理（清 token + reload），与其它接口一致。

把降级放在前端而不是后端自动重试，是为了让重试决策发生在「用户已经看到了什么」之后，同时后端保持无状态、不产生隐藏的重复调用。

## 6. 兼容性与回滚

- **请求契约不变**：`ChatRequest` 字段、默认值、鉴权方式与旧接口相同，客户端把路径从 `/api/chat` 换成 `/api/chat/stream` 即可；
- **旧客户端不受影响**：未更新的前端继续调用 `/api/chat`，行为与改造前完全一致；
- **新客户端可降级**：流式接口不可用（未部署、代理不支持、网络中断）时自动回退旧接口，用户仍能拿到完整回答；
- **日志与数据兼容**：`ChatLog` 表结构未动，流式与非流式写同一张表；`total_tokens`、`latency_ms` 语义一致，运行日志页面无需改动；
- **独立下线 / 回滚能力**：流式端点、前端调用、后端生成器三层可以分别回退，互不牵连——前端把 `submit()` 切回 `await sendChat(...)` 一次性赋值即可，`sendChatStream` 留在 API 层不调用也没有副作用；后端下线路由即可，`ChatService.stream()` 与两个 provider 的 `chat_stream()` 留着也静默；数据库无 schema 变更、无新增依赖、无配置开关，回滚不改环境变量。

## 9. 已知边界与后续

**代理与网络**

- SSE 依赖中间层逐块转发。nginx 默认 `proxy_buffering on` 会破坏流式，代码已带 `X-Accel-Buffering: no` 规避；其它网关需要显式确认缓冲与读超时。
- **当前没有心跳帧**。开 RAG 精排时，`status{retrieving}` 之后到 `meta` 之间可能数秒无字节（CPU 精排约 +4.3–6.2s，见 [docs/05](05.Rerank实验报告.md)），如果中间代理的空闲超时小于这段时间，连接会被切断。后续可在检索前发 SSE 注释帧（`: ping`）保活。
- **不做断线续传**：没有 `Last-Event-ID`，刷新页面或网络切换后只能重新发请求，会重新生成、重复计费。

**取消与日志**

- 客户端主动取消（`AbortController`）时生成器被取消（`GeneratorExit` 不是 `Exception`），不会发 `error`、不会写成功/失败日志；当前也没有「取消」这种日志状态。是否补一条 `cancelled` 记录待定。
- 上游 provider 在流中途断开时，走异常分支写 `failed` 日志，`assistant_output` 只保留已生成部分。

**指标与观测**

- TTFT（`first_token_ms`）与总耗时（`latency_ms`）只写进 `done` 和服务端日志，没有指标上报、没有面板、没有告警；本地一次联调的实测值见 7.4，服务器侧只按 8.2 清单验证，未做时延测量。
- 空回答时 `first_token_ms` 为 `null`，前端不应把它显示成「0ms」；但前端类型目前按 `number` 声明，属于类型与后端的已知偏差，接指标面板时需要收敛。
- `total_tokens` 口径因 provider 而异（DeepSeek usage vs Ollama prompt+eval），不能直接横比；上游不返回 usage 时记为 0。

**模型与体验**

- `deepseek-reasoner` 的思维链与最终回答分开推送，长思维链仍会拉长总耗时；`deepseek-chat` 没有 `reasoning_content`，只会看到 `delta`。
- 老版本 Ollama 没有 `thinking` 字段，模型把思考内联进 `<think>…</think>` 时，只能在流结束后剥离，**流式过程中看不到这段思维链**——这是 provider 能力差异，不是前端 bug。
- 首字时间包含「Prompt 解析 + 会话记忆 + RAG 检索」，开精排时首字主要花在检索上；本地联调中 `meta` 前约 23.9s 是 hybrid 索引 + rerank 冷启动的特例（见 7.4），不是稳态。如果后续要单独度量生成首字，需要把检索与生成的计时拆开。

**兼容与范围**

- 前端依赖 `fetch` + `ReadableStream` + `TextDecoder`，现代浏览器均支持；IE 不支持（项目目标环境本来就不含 IE）。
- 2G 内存服务器上 `RAG_RERANK_ENABLED=false`、`RAG_HYBRID_ENABLED=true`，流式本身不改变这一约束；未做并发压测。
